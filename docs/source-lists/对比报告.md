### 它是怎么来的

`iptv.m3u` 头部的注释写明了：

```
# 实测能播的 IPTV 直连源（合并三个来源，只保留验证通过的）
# 判据：ffmpeg 真解码 —— ≥5 帧 + std>10（有内容）+ 帧差>1.5（画面在动）
# 来源与实测可用率：
#   iptv-org cn.m3u   23 / 145  （16%）  ← 最可靠
#   best-fan          22 / 182  （12%）
#   iptv-search       21 / 917  （2%）
# 仍然缺：CCTV2、CCTV6、CCTV7、CCTV10、CCTV11、CCTV12、CCTV15、CCTV16
```

**所以这 56 条是从 1244 条候选里筛出来的**，可用率高是筛选的结果。

### 🎯 最有价值的发现：CCTV 网关

最后 12 条是**完整的 CCTV 全家桶**，全走同一个网关：

```
http://39.135.34.150:8080/000000001000/{channel_id}/1.m3u8

CCTV-1  综合      …00000001000021973
CCTV-2  财经      …00000001000012442
CCTV-3  综艺      …00000001000011218
CCTV-4  中文国际  …00000001000011219
CCTV-5  体育      …00000001000011220
CCTV-5+ 体育赛事  …00000001000011221
CCTV-6  电影      …00000001000011222

```

**ID 是连续递增的**（11218→11224 差 1，然后跳到 11229、11230）。
按理说 `11225`~`11228` 就是缺的 CCTV-9/10/11/12 —— **但我探测时整个网关返回 HTTP 502**
（连已知在列表里的 CCTV-1 也是 502），所以**无法验证**。

可能原因：网关限地区（国内 ISP）、限 IP、或临时故障。

> **建议**：如果你在国内网络下测，这几个 ID 值得试：
> `1000000001000011225` ~ `1000000001000011228`

## 四、结论与建议

### 两个源的角色完全不同

```
主源        = "什么都有" 的目录（1676 条，覆盖到县级）
              但 91.5% 要走 WebView → 老电视慢、易断

GitHub 源   = "筛过的能播的"（56 条）
              98% 直连 → 秒开、稳定
```

### 对焰火TV 的建议

| 场景 | 用哪个 |
|---|---|
| **老电视模式** | ✅ **只用 GitHub 源**（现状就是对的） |
| **央视** | GitHub 源的 `39.135.34.150` 网关 + CCTV 自有 CDN |
| **省级卫视** | 两边都有，优先 GitHub 源（直连） |
| **县级台** | 只有主源有，但**必须 WebView**，建议标"慢速"或放二级菜单 |

### 主源还可以挖的地方

主源里 **143 条可直连**的地址被埋在 1676 条里。把 `live.html?url=` 这个形态的
**134 条**抠出来（导出时已自动处理，见 `主源.csv` 的 `direct` 列），
就能**不写任何抓取代码**直接扩到播放列表里。
