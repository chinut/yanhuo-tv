# 直播卡顿：参考项目对比分析

分析对象：`土拨鼠大屏浏览器 20260623`（包名 `tv.utao.x5`，versionCode 54）
产物形式：反编译包 —— `resources/` 是编译后资源，`sources/` 是 smali 反编译出的 Java。

结论先行：**我们和它的 WebView 配置几乎一模一样，差距在内核；但我自己有一处改动方向搞反了，那个是主因。**

---

## 一、配置对比：几乎没有差别

它的 WebView 配置在 `sources/T1/c.java`（X5 内核封装）里，`e()` 方法：

```java
settings.setJavaScriptEnabled(true);
settings.setAllowFileAccess(true);
settings.setDatabaseEnabled(true);
settings.setDomStorageEnabled(true);
settings.setNeedInitialFocus(false);
settings.setSupportZoom(false);
settings.setBuiltInZoomControls(false);
settings.setDisplayZoomControls(false);
settings.setUseWideViewPort(true);          // 和我们的取值一致
settings.setLoadWithOverviewMode(true);     // 和我们的取值一致
settings.setMixedContentMode(0);
settings.setMediaPlaybackRequiresUserGesture(false);
settings.setUserAgent("Mozilla/5.0 (Windows NT 10.0; Win64; x64) ... Chrome/131.0.0.0 ...");
settings.setCacheMode(-1);
settings.setJavaScriptCanOpenWindowsAutomatically(false);
settings.setGeolocationEnabled(false);
webView.setScrollContainer(false);
webView.setVerticalScrollBarEnabled(false);
webView.setHorizontalScrollBarEnabled(false);
```

我们的 `TvWebPlayerView`：

| 设置 | 参考项目 | 我们 | 结论 |
|---|---|---|---|
| JS / DOM storage / database | 开 | 开 | 一致 |
| `useWideViewPort` / `loadWithOverviewMode` | true | true | **一致** |
| `mediaPlaybackRequiresUserGesture` | false | false | 一致 |
| 桌面 UA | Chrome/131 桌面 | Chrome/131 桌面 | **逐字一致** |
| 缩放/滚动条 | 关 | 关 | 一致 |
| `mixedContentMode` | `0`（ALWAYS_ALLOW） | `ALWAYS_ALLOW` | 一致 |

**所以"照抄它的设置"这条路是走不通的 —— 我们已经是同一套设置了。**

## 二、真正的差别：三处

### 1. 视频全屏机制（差异最实质）

它走的是标准 `WebChromeClient` 全屏回调（`sources/N1/a.java`）：

```java
public final void j(View view) {      // onShowCustomView
    fullscreen.addView(view);
    fullscreen.setVisibility(0);
}
public final void g() {               // onHideCustomView
    fullscreen.removeAllViews();
    fullscreen.setVisibility(8);
}
```

配合布局 `activity_live.xml` 里一个专门的 `fullscreen` 容器：

```xml
<LinearLayout android:id="@+id/webviewWrapper" .../>   <!-- 网页 -->
<LinearLayout android:id="@+id/fullscreen" android:visibility="gone" .../>  <!-- 全屏视频 -->
<LinearLayout android:id="@+id/notify" .../>          <!-- 加载提示（台名+进度%） -->
```

也就是说：**它让站点播放器自己进入全屏，然后把那个视频 View 直接接管过来铺满屏幕。**

我们的做法是**注入 CSS + JS，强行把 `<video>` 元素撑到 100%×100%**，还写了一套元素清理脚本来藏导航栏。

- 它的方案：**一个 View**，页面其余部分不参与渲染
- 我们的方案：**整页仍在渲染**，只是被 CSS 藏起来了 —— CPU 白烧

### 2. 内核（它真正的护城河）

它是 **X5（腾讯浏览服务）+ 系统 WebView 双内核**，运行时选择：

```java
// UtaoApplication
boolean canX5 = QbSdk.canLoadX5(ctx);
if (用户开了 X5 && canX5) { 用 X5 } else { 回退 WebKit }
```

X5 的 `WebSettings` 还额外开了一组扩展：

```java
IX5WebSettingsExtension ext = webView.getSettingsExtension();
ext.setAcceptCookie(true);
ext.setWebViewInBackground(true);     // ← 后台也保持渲染
ext.setForcePinchScaleEnabled(false);
webView.setWebChromeClientExtension(...);
```

X5 内置**专为国内视频站优化的视频解码**（`com/tencent/tbs/video/`），这是 Chromium WebView 没有的。

### 3. WebView 生命周期

它在 `onDestroy` 里彻底销毁（`sources/tv/utao/x5/a.java`）：

```java
webView.loadUrl("about:blank");
webView.clearHistory();
((ViewGroup) view.getParent()).removeView(view);
webView.stopLoading();
webView.destroy();
```

`onPause` 还会 `setJavaScriptEnabled(false)`，`onStop` 会 `stopLoading()`。

我们复用一个 WebView 实例切台 —— 长时间运行会累积内存和渲染线程。

## 三、它的 WebView 升级机制（对老电视其实无效）

它有一套 `WebViewReplace`，靠反射改 `IWebViewFactory.setPackageInfo()` 来**替换系统 WebView 实现**，并在 `Application.onCreate` 里下载新版 WebView APK。

但看它的版本选择逻辑（`sources/com/webview/update/config/WebViewConfig.java`）：

```java
boolean is64 = Build.SUPPORTED_ABIS[0].contains("64");
if (!is64) {
    return WEBVIEW_75;              // ← 32 位设备只能升到 75
}
if (sdk >= 29) return WEBVIEW_138;  // Android 10+
return sdk >= 24 ? WEBVIEW_119 : 75;
```

**关键：32 位设备只能升到 WebView 75。** 而"带不起来直播"的老电视基本都是 32 位 Android 5.1/6.0 —— **这条升级路对它自己也无效**。

这也解释了为什么这个项目在很多老电视上同样卡：它也没有真正解决内核问题。

## 四、我自己的一个错误（主因）

参考项目有完整的清晰度切换（`domain/RateItem.java`、菜单里的 `rates` 列表），而我在 1.0.17 里做了一件**方向相反**的事：

```kotlin
// LivePlayerScreen.kt
val trackSelector = DefaultTrackSelector(context).apply {
    parameters = parameters.buildUpon()
        .setMaxVideoSize(1920, 1080)
        .setMaxVideoBitrate(20_000_000)   // ← 放开了上限
        .build()
}
```

而央视流的 master playlist 是：

```
BANDWIDTH=1800000  RESOLUTION=1280x720   ← 我当时想"锁最高"
BANDWIDTH=1350000  RESOLUTION=1024x576
BANDWIDTH= 900000  RESOLUTION= 854x480
BANDWIDTH= 600000  RESOLUTION= 640x360   ← 老电视真正能扛的档
```

我当时的理由是"直播宁可缓冲也别糊"，但你的真机反馈是**"试了很多个电视都带不起来"** —— 说明这些设备的解码能力和网络根本吃不下 720p/1.8Mbps。

**正确做法应该是：起步选低档，让自适应往上探。** 解码跟不上时 ABR 会自动回退到能扛的档位。

另外 15 秒的 `minBufferMs` 对老电视也偏重（低内存设备上反而更容易被系统杀或抖动），8 秒更合适。

## 五、优化方案

### 立即可做（低风险，直接改）

| # | 改动 | 理由 |
|---|---|---|
| 1 | **起步档位降下来**：`setMaxVideoSize` 按设备能力给上限，让 ABR 自己往上探 | 修掉我搞反的方向；这是当前卡顿的主因 |
| 2 | 直播缓冲 15s → 8s | 老电视内存吃紧，过大的缓冲反而有害 |
| 3 | 让 WebView 的 `onShowCustomView` 全屏机制可用 | 学参考项目：一个 View 铺满，不再让整页参与渲染 |

### 需要评估（高风险，改动大）

| # | 方案 | 代价 |
|---|---|---|
| 4 | 接入 X5（TBS）内核 | SDK 需运行时下载 ~40MB（腾讯 2024 起已停止维护，服务稳定性存疑）；老电视存储紧张；需大改播放层 |
| 5 | 照搬 WebViewReplace 反射替换 | 只对 64 位/Android 7+ 有效；32 位老电视仍只能到 75，**对目标设备无效** |

**我的建议：先做 1–3。** 这三项风险低、改动小，而且第 1 项大概率就是主因。做完若真机仍不理想，再评估第 4 项 —— 但那时要接受"X5 服务可能随时不可用"的风险。

---

## 六、诚实的边界

- 上面所有结论都来自**读反编译代码**，没有在真机上对比验证
- 参考项目本身在老电视上也未必流畅（它的内核选择逻辑说明它也没有更好办法）
- 最终是否改善，**只能在你的电视上实测**
